REQUIREMENTS FORM – Documentation + Design Pattern Justification
Language: English (recommended for the submission form)

------------------------------------------------------------
CORE GAMEPLAY REQUIREMENTS
------------------------------------------------------------

1) Requirement: Player explores in a dungeon (dungeon can be either manually made or procedurally generated) to kill procedurally generated enemies.
Documentation: 	
Design pattern justification: Event/Observer style is used for kill notifications (`CombatEvents.OnEnemyKilled`) so gameplay systems (XP, quests, spawners) react to enemy deaths without tight coupling.

2) Requirement: When enemies are killed, they drop items, and the player gains XP.
Documentation: Enemy drop + XP is handled by:
- Drops: `EnemyHealth` → `TryDropItems()` spawns pickup objects based on `EnemyConfig.drops` (DropEntry list). Item pickup visuals can be set via `ItemData.pickupPrefab`.
- XP: `PlayerProgression` subscribes to `CombatEvents.OnEnemyKilled` and awards `EnemyConfig.xpReward`.
Design pattern justification: Observer pattern via `CombatEvents` decouples “enemy died” from “give XP” and “update quests/spawners”.

3) Requirement: The players can pick up items and store them in the inventory.
Documentation: Picking up items is handled by `PlayerInteraction` (Press F when close). Inventory storage is managed by `InventoryManager` (singleton in scene). Item pickups use `ItemPickup` components (with `ItemData` + quantity).
Design pattern justification: Singleton pattern is used for `InventoryManager` to provide a single inventory source of truth across the game; UI/quests subscribe to `InventoryManager.OnInventoryChanged` (Observer/event pattern).

4) Requirement: The player can level up when they get enough XP, as the player levels up, they become more powerful in certain ways.
Documentation: Leveling is implemented in `PlayerProgression`. XP is gained on enemy kill, and when `currentXP >= xpToNextLevel`, `LevelUp()` runs. Power growth is applied by increasing `damageMultiplier` and `PlayerHealth.maxHP` (and healing on level up).
Design pattern justification: Observer/event pattern is used: `PlayerProgression.OnXPChanged` / `OnLevelUp` can drive UI updates (HUD) without the HUD polling.

------------------------------------------------------------
ENEMY SPAWNING SYSTEM REQUIREMENTS
------------------------------------------------------------

5) Requirement: The system can spawn at least 2 types of regular enemies and 1 boss enemy.
Documentation: Regular enemies are spawned by `EnemySpawner`:
- `Spawner_Normal`: `enemyTypeA = Goblin`, `enemyTypeB = None`.
- `Spawner_Mages`: `enemyTypeB = SkeletonMage`, `maxAlive = 1`, `spawnPoints = MagePoint1, MagePoint2`, `useSequentialSpawnPoints = true`.
Boss is spawned with `BossSpawnTrigger` (trigger collider) which instantiates the boss prefab at `BossSpawnPoint`.
Design pattern justification: Data-driven configuration via ScriptableObjects (`EnemyConfig`) allows multiple enemy types with different stats without hardcoding.

6) Requirement: Enemies can attack and hurt player to reduce HP, when HP is 0 the game is over.
Documentation: Player HP is handled by `PlayerHealth`. Regular melee enemies attack via `EnemyAI` (attackRange + attackCooldown + contactDamage). Stationary mage attacks via `MageTurretAI` (projectile). Game over is triggered in `PlayerHealth.Die()` → `GameManager.HandlePlayerDied()` which shows `GameOverUI` and allows restart.
Design pattern justification: Singleton pattern for `GameManager` (global game state), plus event hooks (`PlayerHealth.OnDied`) to let UI react.

7) Requirement: Different enemy type should have different visuals, different attributes, the boss enemy should have multiple behaviours (multiple types of attacks, multiple attack patterns, etc.)
Documentation: Different enemy types use different prefabs and different `EnemyConfig` assets (different stats and rewards). Boss behaviours are configured via `BossController` + `BossAttackDefinition` assets (two attacks configured in the inspector with cooldown, range, windup, animation trigger).
Design pattern justification: Strategy pattern (data-driven) is applied to the boss: each `BossAttackDefinition` acts as a configurable “attack strategy” selected/executed by `BossController` without hardcoding each attack in code.

8) Requirement: Each enemies’ max HP and current HP are clearly displayed.
Documentation: Each enemy prefab has `EnemyHealth` + `EnemyHealthBar` (world-space UI) which listens to `EnemyHealth.OnHealthChanged` and displays current/max HP above the enemy. `EnemyHealthBar.autoOffsetFromTarget` keeps it positioned above the model.
Design pattern justification: Observer/event pattern (`EnemyHealth.OnHealthChanged`) updates UI without polling.

------------------------------------------------------------
BATTLE SYSTEM REQUIREMENTS
------------------------------------------------------------

9) Requirement: The game should clearly indicate when player and enemy are attacking (projectiles fired, melee attack animation, on-screen text description, etc.).
Documentation: Player attacks are handled by `PlayerCombat` (left click melee / right click alt attack, optionally fireball). Enemy attacks are handled by `EnemyAI` (melee) and `MageTurretAI` (projectile). On-screen feedback uses `CombatTextManager` (e.g., ATTACK/CAST text).
Design pattern justification: Centralized feedback via `CombatTextManager` (singleton-like service) keeps combat feedback consistent and avoids duplicating UI logic across scripts.

10) Requirement: The game should clearly indicate when player and enemy are hurt.
Documentation: Damage/heal feedback is shown by:
- Floating combat text via `CombatTextManager` (PlayerHealth and EnemyHealth call it).
- Enemy HP bars via `EnemyHealthBar`.
Design pattern justification: Observer/event pattern for HP changes + a single UI spawning service for combat text.

------------------------------------------------------------
QUEST SYSTEM REQUIREMENTS
------------------------------------------------------------

11) Requirement: The quest system gives at least 2 quests, 1 “kill x amount of certain type of enemies” quest and 1 “fetch a certain item from the dungeon” quest.
Documentation: Quests are defined with `QuestDefinition` ScriptableObjects:
- Kill quest: type `KillEnemy` with `targetEnemyId` matching `EnemyConfig.enemyId`.
- Fetch quest: type `FetchItem` with `targetItem` set to the `ItemData`.
Active quests are started automatically in `QuestManager.startingQuests` (no NPC).
Design pattern justification: Data-driven design via ScriptableObjects (`QuestDefinition`) makes quests customizable without hardcoding.

12) Requirement: The system clearly indicates the progress of the quests on GUI.
Documentation: `QuestHUD` displays active quests from `QuestManager.ActiveQuests` and updates on `QuestManager.OnQuestsChanged`. Completed quests are color-coded green.
Design pattern justification: Observer/event pattern (`OnQuestsChanged`) updates UI without polling.

------------------------------------------------------------
PLAYER INVENTORY SYSTEM REQUIREMENTS
------------------------------------------------------------

13) Requirement: The system manages items gained from killing enemies.
Documentation: Drops are produced by `EnemyHealth` using `EnemyConfig.drops`. Pickups are collected via `PlayerInteraction` and stored in `InventoryManager.items`. A pickup sound is played on successful add (`InventoryManager.pickupItemSfx`).
Design pattern justification: Singleton + event-driven updates (`InventoryManager.OnInventoryChanged`) to keep UI/quests synchronized.

14) Requirement: There is one mandatory item: HP potion, player should be able to use it to recover health.
Documentation: HP potion is an `ItemData` with `isConsumable=true` and `healthRestore>0`. Using an item from inventory calls `InventoryManager.UseItem()` which heals `PlayerHealth.TryHeal()` and removes one unit from inventory.
Design pattern justification: The inventory “UseItem” is a simple command-like entry point; effects are data-driven via `ItemData` fields (healthRestore).

------------------------------------------------------------
GUI REQUIREMENTS
------------------------------------------------------------

15) Requirement: The GUI should be resolution independent.
Documentation: The Canvas uses `Canvas Scaler` with “Scale With Screen Size” (configured in Unity). All HUD elements are under the Canvas so they scale across resolutions.
Design pattern justification: Not applicable (Unity UI configuration).

16) Requirement: The GUI should display the following information in clear manners: Player’s max HP, current HP. Player's current level, XP required to level up. Quests information and progress.
Documentation:
- Player HP: `PlayerHUD` listens to `PlayerHealth.OnHealthChanged` and updates HP text/slider.
- Level/XP: `PlayerHUD` listens to `PlayerProgression.OnXPChanged`.
- Quests: `QuestHUD` reads from `QuestManager` and updates on `OnQuestsChanged`.
Design pattern justification: Observer/event pattern keeps UI decoupled from gameplay logic.

17) Requirement: The GUI system can show and hide player inventory.
Documentation: `InventoryUI` toggles the inventory panel on key `E`. When opened, game is paused (`Time.timeScale = 0`) and cursor is unlocked; when closed, cursor is locked again.
Design pattern justification: Not applicable (UI state toggling).

QUALITY REQUIREMENTS
------------------------------------------------------------

18) Requirement: Proper visual assets (self-made and/or external) are used.
Documentation: Enemy/player visuals are set via prefabs (Goblin, SkeletonMage, Boss). Item visuals use icons and world pickup prefabs (e.g., `HealthPotion_Pickup` assigned in `ItemData.pickupPrefab`). UI uses TextMeshPro and icons.
Design pattern justification: Not applicable.

19) Requirement: The game can be presented as a suitable portfolio item, which means the game can't have obvious bugs or contain too many placeholders.
Documentation: The project includes on-screen combat feedback, HP bars, quests HUD, functional inventory, and Game Over UI with restart. A full test path is documented in `README.md` (controls + how to test systems). Console warnings/logs exist to diagnose missing configuration (e.g., animation parameters).
Design pattern justification: Decoupled systems (event-driven) reduce bug-prone coupling and make it easier to test/iterate quickly.

20) Requirement: Project uses a clear hierarchy and asset structure, with descriptive (Scene) names and a clear GameManager in the Hierarchy.
Documentation: Use `Assets/OutdoorsScene.unity`. The Hierarchy should contain `GameManager`, `InventoryManager`, `QuestManager`, `Canvas` (HUD/Inventory/GameOver), and spawners (`Spawner_Normal`, `Spawner_Mages`). Assets are separated under `Assets/Scripts/...` and `Assets/Prefabs/...`.
Design pattern justification: Singleton pattern ensures a clear “single instance” manager hierarchy (GameManager/InventoryManager/QuestManager).

21) Requirement: The project runs with no exceptions.
Documentation: During playtest, Unity Console should have no red errors. Trigger fallback and multiple GetComponent fallbacks were added to avoid missing-reference crashes. `README.md` includes quick troubleshooting steps.
Design pattern justification: Defensive programming + decoupled event-driven updates reduce runtime errors from missing references.

22) Requirement: After game over, game can be restarted or returned to a check point without closing and reopening.
Documentation: `PlayerHealth` triggers `GameManager.HandlePlayerDied()` at 0 HP. `GameOverUI` shows a panel with a Restart button that calls `GameManager.Restart()` to reload the active scene.
Design pattern justification: Singleton pattern (`GameManager`) centralizes restart logic; UI calls a single restart entry point.

23) Requirement: Instructions on how to use test scenes in this row under documentation and/or instructions on how to enable debugging and testing options per the Good rubric under Unit Test, please add the instructions in this row under Documentation.
Documentation: See `README.md` for: scene to open, required objects in hierarchy, controls, how to test quests/spawners/boss, and quick troubleshooting. Debug options include enabling `BossSpawnTrigger.debugLogs`, `InventoryUI.debugButtonLogs`, and other script debug toggles exposed in the Inspector.
Design pattern justification: Not applicable (documentation requirement).
